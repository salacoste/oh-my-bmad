## Story

As **R2d2 (operator + sole maintainer)**,
I want **every Platform-published Docker image to be signed via cosign keyless against the GitHub Actions OIDC identity**,
so that **the operator's deploy-side `cosign verify` proves the image was published by the canonical `release.yml` workflow — closing the third of three supply-chain triumvirate gates (SBOM in 8.1, SLSA L2 in 8.2)**.

## Acceptance Criteria

1. **(AC-1)** Every image published by `release.yml` (1 base + 7 services = 8 images per release) carries a cosign keyless signature, generated by `cosign sign --yes` against the image's content digest, with the signing certificate minted from the workflow's GitHub Actions OIDC identity.
2. **(AC-2)** `cosign verify --certificate-identity-regexp "^https://github.com/${OWNER}/oh-my-bmad/\.github/workflows/release\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+(-[A-Za-z0-9.-]+)?$" --certificate-oidc-issuer "https://token.actions.githubusercontent.com" <image>@<digest>` succeeds for every released image; signature certificate identity matches the canonical workflow path + a well-formed semver tag. **Story 8.3 pass-2 F1+F3**: regexp anchored on BOTH ends (`^...$`) AND matches only valid semver — prevents fork-attestation spoofing AND suffix-injection. (Carry-over from Story 8.2 pass-2 lesson.)
3. **(AC-3)** No new top-level `permissions:` additions required — Story 8.2's `id-token: write` already covers cosign keyless OIDC. `packages: write` (existing) covers signature push to GHCR. **Story 8.3 pass-2 F13 note:** cosign v2.x auto-detects `GITHUB_TOKEN` from the Actions environment (via `ACTIONS_ID_TOKEN_REQUEST_URL`) for the registry-write half; no explicit `--registry-username` / `--registry-password` flags required. The permission chain `packages: write` → `GITHUB_TOKEN` → cosign's GHCR push is implicit but documented here for permission-audit traceability.
4. **(AC-4)** `sigstore/cosign-installer` SHA-pinned to a canonical release: `sigstore/cosign-installer@6f9f17788090df1f26f669e9d70d6ae9567deba6  # v4.1.2` (released 2026-05-07). Follows the existing release.yml convention.
5. **(AC-5)** Cosign binary installed once per job via the installer action; `cosign sign --yes <image>@<digest>` runs after both Story 8.1 SBOM and Story 8.2 SLSA attestation steps (signature is the outermost wrapper of the supply-chain triumvirate).
6. **(AC-6)** Failure isolation per layer:
   - **Service matrix entry failure:** if signing fails for any service, that service's matrix entry fails (consistent with `fail-fast: false` matrix isolation from Stories 8.1/8.2). Sibling services continue.
   - **Base job signing failure (pass-2 F9 carry-over from 8.2 pass-2 F9):** the base job is a singleton (not a matrix). Cosign sign failure on the base image fails the entire `build-and-push-base` job, which cascades to `needs: build-and-push-base` blocking the entire services matrix — no service is built unattested. This is the intended hard-block per ADR-0008. The `validate-digest-base` step (Story 8.2 pass-2 F2) is the primary fail-loud contract; the cosign sign step's own `if:` is defense-in-depth.
   - **Sigstore Fulcio/Rekor outage:** hard release block per ADR-0008 §F8 (no `continue-on-error`). The cosign sign step waits for Rekor inclusion before returning success.
7. **(AC-7)** Workflow YAML lint + actionlint pass; SHA-pin grep returns 2 (cosign-installer at 2 sites) + 2 (`cosign sign` steps).
8. **(AC-8)** Implementation artifact (this file) + sprint-status entry transitioned `backlog` → `ready-for-dev` → `in-progress` → `review` → `done`.

## Dev Notes

### Why keyless signing, not key-managed

- **Keyless (chosen):** signing identity is the GitHub Actions workflow's OIDC token; certificate from Sigstore Fulcio is minted per signing operation and trusted via Rekor transparency log. No long-lived signing key to manage, rotate, or leak.
- **Key-managed (rejected):** would require an HSM or environment-stored signing key. Adds key-rotation procedure, secret-leak attack surface, and operational overhead. Out of scope for the solo-operator threat model — per ADR-0008 §"GitHub-first-party SLSA over external Sigstore CI", we explicitly chose keyless to minimize trust-perimeter operational cost.

### Why `cosign sign --yes`, not `cosign sign --keyless` or other flag forms

- Modern cosign (v2.x+) defaults to keyless mode when no `--key` argument is provided. `--yes` is the only required flag in non-TTY environments to suppress the confirmation prompt for "are you sure you want to use keyless? (this will create a Rekor entry)".
- Older `cosign sign-blob` is for raw-file signing (not OCI images) — not applicable here.

### Where to insert the cosign install + sign steps

For consistency with the existing supply-chain ordering pattern (Stories 8.1 SBOM after `:latest` tag; 8.2 SLSA before SBOM), the cosign sign step lands **after** SBOM generation but **before** the SBOM artifact upload. Rationale: signing is the outermost wrapper — sign the image digest *after* the image is fully attested with SLSA + has an SBOM, so the signature covers an image whose triumvirate is complete.

Insertion order in both jobs (updated post-8.4 + pass-2):
1. Build + push (existing, Story 1.8/1.9)
2. Tag `:latest` (existing, Story 1.9)
3. **NEW: Validate build digest before attestation** (Story 8.2 pass-2 F2)
4. **SLSA L2 attestation** (Story 8.2)
5. SBOM generation (Story 8.1)
6. **Install cosign** (Story 8.3) — `cosign-release: 'v2.4.1'` pinned per pass-2 F10
7. **cosign sign** (Story 8.3) — `id: sign-base`/`sign-service` per pass-2 F12
8. **cosign attest SBOM** (Story 8.4) — shipped after 8.3, attaches the SBOM as a Sigstore attestation
9. Upload SBOM artifact (Story 8.1)

**Story 8.3 pass-2 F5 correction:** the original insertion-order list (7 steps) was written before Story 8.4 shipped. The list now reflects the full 9-step pipeline including 8.4's `cosign attest SBOM` and 8.2 pass-2's `Validate build digest` prelude. Both jobs follow the same ordering with matrix-specific image references.

### Tag-retry / Rekor-duplicate behavior

Per **ADR-0008 §"Operational policy notes" F7** (added post-Story 8.2 pass-2): re-pushing the same `v*` tag (or `gh run rerun` after partial failure) creates duplicate Rekor entries for cosign sign. This is **cosmetic, not a security issue** — `cosign verify` validates the Fulcio cert SCT + Rekor inclusion proof for each candidate entry, automatically skipping entries from failed signing attempts. Operators should NOT panic on duplicate Rekor entries; they confirm idempotent retry semantics, not key compromise. (Story 8.3 pass-2 F6 cross-reference.)
