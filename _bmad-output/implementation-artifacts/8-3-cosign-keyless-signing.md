## Dev Notes

### Why keyless signing, not key-managed

- **Keyless (chosen):** signing identity is the GitHub Actions workflow's OIDC token; certificate from Sigstore Fulcio is minted per signing operation and trusted via Rekor transparency log. No long-lived signing key to manage, rotate, or leak.
- **Key-managed (rejected):** would require an HSM or environment-stored signing key. Adds key-rotation procedure, secret-leak attack surface, and operational overhead. Out of scope for the solo-operator threat model — per ADR-0008 §"GitHub-first-party SLSA over external Sigstore CI", we explicitly chose keyless to minimize trust-perimeter operational cost.

### Why `cosign sign --yes`, not `cosign sign --keyless` or other flag forms

- Modern cosign (v2.x+) defaults to keyless mode when no `--key` argument is provided. `--yes` is the only required flag in non-TTY environments to suppress the confirmation prompt for "are you sure you want to use keyless? (this will create a Rekor entry)".
- Older `cosign sign-blob` is for raw-file signing (not OCI images) — not applicable here.

### Where to insert the cosign install + sign steps

For consistency with the existing supply-chain ordering pattern (Stories 8.1 SBOM after `:latest` tag; 8.2 SLSA before SBOM), the cosign sign step lands **after** SBOM generation but **before** the SBOM artifact upload. Rationale: signing is the outermost wrapper — sign the image digest *after* the image is fully attested with SLSA + has an SBOM, so the signature covers an image whose triumvirate is complete.

Insertion order in both jobs:
1. Build + push (existing, Story 1.8/1.9)
2. Tag `:latest` (existing, Story 1.9)
3. **SLSA L2 attestation** (Story 8.2)
4. SBOM generation (Story 8.1)
5. **NEW: Install cosign** (Story 8.3)
6. **NEW: cosign sign** (Story 8.3)
7. Upload SBOM artifact (Story 8.1)
