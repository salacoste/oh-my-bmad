## Lessons learned

### L1 — Validation-FIRST (verify the external tool BEFORE coding) prevented 3 wrong implementations
**Pattern:** every litestream story hinged on a fact I'd otherwise have guessed wrong, and verifying it first (docs + source + a hermetic local run) caught the defect before it shipped:
- **13.1:** the `:ro` mount I initially wrote was a CRITICAL defect — litestream needs the DB dir WRITABLE (it writes a `.state.sqlite3-litestream/` meta dir + checkpoints the DB). Caught by authoritative doc/source verification before push.
- **13.3:** I PROVED the `replicate→restore` round-trip locally (hermetic `file` replica) BEFORE writing the recipe — the commands were verified, not guessed.
- **13.4a:** the "is sync_count a reliable heartbeat when idle?" assumption (which gates whether a flat counter = hang) was EMPIRICALLY confirmed (idle DB → sync_count 4→8→12) before building the silent_stall branch.
**Conclusion:** for any story integrating an EXTERNAL tool whose runtime behavior the design depends on, verify the behavior (official docs + source + a hermetic local reproduction) BEFORE writing the integration. The cost (one subagent + a 10s docker run) is trivial vs shipping a broken `:ro` mount or a false-positive lag signal.
**Action AI-13.1:** add "external-tool behavior verified (docs/source/hermetic run)" as an explicit dev-story checklist item for any story whose scope includes a third-party binary/service.

### L2 — The cross-uid event-log file-mode bug is SYSTEMIC and RECURRED
**Discovery:** 13.4's emit script (`check_replication_lag.py`) copied the FR26 flock-append pattern from `scripts/emit_signature_rejected.py` (Story 8.6) — including its **pre-11.3.11 `0o640`** file-create mode. The diff-audit caught it: an external emitter creating the day's JSONL at `0o640` (group-non-writable) crash-loops registry-state's cross-uid recovery — the EXACT bug Stories 11.3.8/11.3.11/11.3.12 fixed for the in-service writers. Fixed here to `0o660 + os.fchmod`.
**Conclusion:** this is the SYSTEMIC umask-022 / cross-uid-group-write gap (events-dir, events-file, sqlite-WAL were all the same root). It KEEPS recurring because each writer reimplements file-create independently, and the canonical-but-stale precedent (`emit_signature_rejected.py`) still carries `0o640`.
**Action AI-13.2 (HIGH — carry to Phase-2 closure):** (a) fix `emit_signature_rejected.py` to `0o660+fchmod` (it has the same latent bug, un-fixed). (b) extract ONE shared `append_event_line(path, line)` helper in `packages/events` that bakes in `0o660 + os.fchmod` so no future external emitter can reintroduce `0o640`. (c) consider whether a container umask of `002` (vs current 022) is the real systemic fix — but verify it does NOT make the audit DB world-readable (empirically 002 → 0o664, which IS world-readable for audit files — so the per-file fchmod approach is safer than a blanket umask change).

### L3 — Baseline/cardinality bumps must update ALL assertions; integration tests hide staleness
**Discovery:** 13.4 found `tests/integration/test_metrics_cardinality.py` STALE at `61` — Stories 12.2 (+1) and 12.3 (+1) had bumped the UNIT cardinality tests (`test_metrics_state.py`) but never propagated to the INTEGRATION cardinality test, which runs only in nightly/compose (not the PR gate), so the staleness went unnoticed for two stories. 13.4 reconciled it to the empirically-verified 64.
**Conclusion:** when a change has a "magic number" assertion in MORE than one test (unit + integration), a partial update silently rots the un-run one. Nightly-only tests are the blind spot.
**Action AI-13.3:** for cardinality (and any cross-test baseline), prefer a SINGLE source of truth (a derived constant the tests import) over duplicated literals; failing that, grep ALL assertions of the number when bumping.

### L4 — The architect-design → executor-build → orchestrator-diff-audit → 3-lane review pipeline scales
**Pattern:** the hardest story (12.3a, cross-session) used a read-only architect design pass to resolve the inbound-channel crux (extend the existing JSONL tail) BEFORE any code, then executor build, then diff-audit, then 3-lane. Epic 13's stories used the lighter explore→build→audit→single-review where appropriate. The heavier pipeline was reserved for genuine cross-service/authorization complexity.
**Conclusion:** match review weight to codebase-impact (Epic-11 AI-1), and front-load an architect design pass for any story with a genuine cross-service architecture decision — it prevents building the wrong coupling.
