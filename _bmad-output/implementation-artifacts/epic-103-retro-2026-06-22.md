# Epic 103 Retrospective — Event Timeline / Transitions Live-Read Runtime Boundary

## Scope reviewed

Epic 103 closed Phase 24 for the Event timeline / transitions live-read runtime boundary:

- Story 103.1 selected exactly `GET /v1/tasks/{task_id}/events` and `GET /v1/tasks/{task_id}/transitions` and opened Phase 24 as docs/status-only planning.
- Story 103.2 implemented the narrow browser/runtime boundary for those two routes in `dashboard/static/event-timeline.js`.
- Story 103.3 completed docs/status final closure after repaired planning consensus, push, remote CI run `27967910766`, and final docs/status review.

This retrospective is no-blame and systems-focused. It captures what the workflow learned from Phase 24 closure and prepares the next dashboard live-read route-family planning slice.

## Part 1 — Epic Review

### What went well

1. **Critic caught scope and CI ambiguity before execution.** The first Story 103.3 Critic pass blocked the plan until closure wording and CI failure handling made it impossible for a docs/status story to absorb non-doc/runtime failures.
2. **The route boundary stayed narrow.** Epic 103 closed only the event/transition route family and did not expand into trace, history/replay, lifecycle readiness, task-list/search/discovery, aggregate/session/digest, generated live data, or mutation/control surfaces.
3. **Final closure commit CI gating worked.** Story 103.3 treated closure as incomplete until the final docs/status closure commit had remote CI evidence or a documented no-run condition.
4. **Direct CI confirmation avoided a false blocker.** `gh run watch` hit an API timeout, but direct `gh run view` confirmation established that the relevant run completed successfully.
5. **Guardrail repetition paid off.** Repeated exact-route and deferred-surface wording prevented Phase 24 closure from being read as broad dashboard live wiring.

### What created friction

1. **Closure status can still outrun external evidence.** Story 103.3 needed explicit language that CI failures outside docs/status scope return to ralplan or a reopened implementation repair story.
2. **Tool-level CI polling is not enough.** `gh run watch` can fail due to API timeout even when the run succeeds, so workflow evidence needs a fallback confirmation path.
3. **Trace adjacency increased semantic-drift risk.** Event rows can contain `trace_id`, but Phase 24 correctly kept trace correlation out of the event/transition runtime boundary.
4. **Docs/status closure needs the same rigor as runtime work.** YAML/status wording can change project truth and therefore needs review, CI, and a clean final gate.

### Lessons learned

- **L1 — Critic scope blocks are useful before execution.** When a Critic identifies ambiguous closure scope or CI handling, repair the plan before changing docs/status truth.
- **L2 — Final closure commit CI is a release gate.** A phase should not be terminally closed until the commit that changes closure/status truth has remote CI success or documented no-run evidence.
- **L3 — `gh run watch` is not the only source of CI truth.** If watch/polling times out, use direct `gh run view` evidence against the expected run/head SHA before treating CI as unknown or failed.
- **L4 — Adjacent route metadata is not route authorization.** `trace_id` values visible in event/transition rows may motivate a future trace-correlation story, but they do not authorize trace runtime wiring by themselves.
- **L5 — Deferred surfaces must stay named.** History/replay, lifecycle readiness, task-list/search/discovery, and aggregate/session/digest are higher-risk and should remain fail-closed unless a future planning gate explicitly selects them.

## Part 2 — Next Epic Preparation

### Selected next planning candidate

Phase 25 should open **Trace correlation** as the next narrow dashboard live-read route-family planning branch:

- `GET /v1/trace/{trace_id}`

### Why this is the next safest slice

1. It naturally follows Event timeline / transitions because event and transition rows may display trace identifiers as provenance metadata.
2. It remains one route family with one required identifier, `trace_id`.
3. It can be planned as route selection before implementation, preserving the same docs/status-first pattern used by Phases 23 and 24.
4. It is narrower than history/replay, lifecycle readiness, task-list/search/discovery, and aggregate/session/digest.
5. It can require strict guardrails before runtime work: no trace search/list, no event or task discovery, no replay/snapshot/lifecycle action, and no aggregate/session join.

### Non-goals for the next opening story

Phase 25 Story 104.1 must not authorize:

- runtime implementation;
- backend/API route expansion;
- browser `fetch`, XHR, WebSocket, EventSource, polling, storage/cache, workers, service workers, hidden clients, or additional scripts;
- trace search/list/discovery, hidden trace lookup, automatic trace traversal, replay, history, lifecycle readiness, task-list/search/discovery, aggregate/session/digest, stream, generated live data, or mutation/control surfaces;
- `event_id`, `task_id`, or `session_id` as route selectors for trace lookup unless a future runtime story proves a visible, explicit, non-discovery `trace_id` source;
- dependency, lockfile, CI, deployment, service, MCP, package, or generated-data changes.
