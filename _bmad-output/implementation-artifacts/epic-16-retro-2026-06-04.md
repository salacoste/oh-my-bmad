# Epic 16 Retrospective: τ github MCP server — first recipe reuse + G-SEC-2 (Phase 3 Epic 3 of 6)

## Epic Summary

Epic 16 shipped `github-mcp` — the most operator-visible fleet server and the **first reuse of the
ADR-0010 recipe** (proving it transfers from the reference implementation). It exposes
issues/PRs/reviews `list`/`get` (Tier-1) + create/update/request-review/comment (Tier-3
approval-gated), authenticated with a **narrowly-scoped credential** (`GITHUB_MCP_SCOPED_TOKEN`),
emitting `github.*` events. 6 stories, PRs #43–#47, all CI-green. Closes the **MCP-subprocess half
of G-SEC-2** (the broad `GITHUB_TOKEN` no longer reaches any MCP child).

The epic's defining characteristic: it validated that the recipe *reuses* (a different archetype —
a REST client, not a subprocess sandbox), and it is where **diff-audit discipline caught a P0
credential-leak the delegated pass shipped**, and where an **independent security review corrected a
scoping over-claim** I would otherwise have committed.

## Key Lessons (3 — carried forward to Epics 17–19)

### L1: A tool result is a disclosure surface — never echo a credential, even "for the test"
The 16.3 leak was *plausible*: the scoped-credential contract needed to assert "auth uses the scoped
token," and returning the token made that trivially testable. But returning a secret through the
tool boundary IS the leak. The correct contract records the *outbound* `Authorization` header (via a
recordable adapter), never the returned token. Every store/REST server inherited "no secret echoed
in any result" as a diff-audit checkpoint.

### L2: Independent review catches over-claims, not just bugs
On 16.5 the *code* was correct (LOW risk, byte-identical allowlist, no broad secret). What the
independent security-reviewer caught was a **framing error** — I'd have committed "closes G-SEC-2"
when only half the threat was closed. Precision in security claims matters: a half-closed gap labeled
"closed" stops anyone from finishing it. The separate lane saw what the author (me) was too close to.

### L3: The recipe reuses across archetypes — but the security model is per-archetype
git-mcp's threat was repo-local-config RCE; github-mcp's is broad-credential leakage. The recipe
(tiering, trace_id, allowlist, separability, supply-chain) transferred verbatim, but the *credential
model* is github-specific (scoped token, the only credential in the whole fleet allowlist). ADR-0010
§6's "scoped credentials use new, narrowly-named vars" was the load-bearing exception.
