# Epic 17 Retrospective: υ verification MCP server — sandboxed build/test runner (Phase 3 Epic 4 of 6)

## Epic Summary

Epic 17 shipped `verification-mcp` — a sandboxed build/test runner returning structured
`{pass/fail, logs, coverage}`, the **closest sibling to git-mcp** (both run subprocesses confined
to the worktree). Tools are Tier-2 (`run_build`/`run_tests` — they run project code but perform no
external mutation), emitting `verification.completed` events. 5 stories, PRs #48–#51, all CI-green.
The cleanest epic — no security defect surfaced, because the sandbox primitives were lifted
verbatim from git-mcp's proven `GitExecutor`.

## Story-by-Story Highlights

- **17.1 + 17.2 (PR #48):** ATDD + scaffold. `VerificationExecutor` mirrors `GitExecutor`:
  `asyncio.create_subprocess_exec` (never `_shell`), cwd pinned to the worktree, child-env =
  secret-free `_ENV_ALLOWLIST` (PATH/HOME/locale/PYTHONPATH/VIRTUAL_ENV — explicit "never add
  `*_TOKEN`/`*_KEY`/`*_SECRET`"), wall-clock timeout + kill/reap → `VerificationTimeout`, realpath
  `_contains` containment. The uv hook-deadlock recurred (adding the workspace member); broke it
  with the Monitor tool.
- **17.3 (PR #49):** `run_build`/`run_tests` Tier-2; path-escape refused before spawn; non-zero exit
  → `pass=False` (never raised); spawn-failure → structured fail.
- **17.4 (PR #50):** `verification.completed` events (two-location, 1.1.0); payload = recipe + exit-
  status + pass/fail (no logs/secrets in the queryable event).
- **17.5 (PR #51):** S-7 separability + allowlist (`VERIFICATION_MCP_*`, all non-secret — no
  credential, so authored in main with no separate security-review lane) + supply-chain.

## Key Lessons (2)

### L1: The sandbox primitives ARE the containment for a code-executing server
verification runs arbitrary project build/test code — there is no way to make that "safe" in the
RCE sense. The containment is: cwd-pinned to the worktree + secret-free env-allowlist (so the code
can't read an operator secret to exfiltrate) + wall-clock timeout (so a hung/forkbomb run is killed)
+ realpath containment (so a path arg can't escape). Lifting these verbatim from git's `GitExecutor`
meant no new security surface — the *reuse* was the safety.

### L2: Match review weight to credential/threat profile
Unlike git (RCE) and github (credential leak), verification carries **no credential** and runs
*inside* the already-untrusted worktree. Its `_ENV_ALLOWLIST` vars are non-secret (a worktree path +
actor identity). So 17.5's allowlist change was authored in the main context but needed **no
separate security-review lane** (git-style non-credential risk profile) — a calibrated decision, not
a skipped step.

## Process Improvements (1)
- **Calibrate the review lane to the threat, not the file.** Touching `_ENV_ALLOWLIST` triggers a

  changes (github 16.5). Non-secret vars (git/verification/memory/artifact) get the main-context
  diff-audit, no separate lane — proportionate.
