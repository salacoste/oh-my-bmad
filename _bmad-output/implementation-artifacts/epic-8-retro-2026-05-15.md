## Phase 2 Opening — Was the Brainstorming Right?

Epic 8 was chosen as **γ-first** in the Phase 2 brainstorming (Narrative I, Observability Phase) because:
- It's the cheapest to land (no new services, no schema changes)
- It hardens every later release (Stories 9-13 inherit the signed pipeline)
- The trust boundary is well-understood (Sigstore is industry-standard)

**In retrospect:** correct call. Epic 8 finished in a single session with minimal architectural disruption. The pipeline now lives in `release.yml` and is the backdrop for every Phase 2 release. If Epic 8 had landed later (e.g., after Epic 9 trace_id), every interim release would have shipped unsigned, accumulating attestation debt.

## Key Lessons (4 — worth carrying forward to Epic 11)

### L1: Static reviews can't predict runtime version-skew bugs

Pass-1 + Pass-2 adversarial reviews caught 57 findings across Stories 8.2-8.6 — including detailed cert-identity regexp anchoring, digest-format validation, FR26 single-writer carry-outs, and 8-terminal-state failure-mode tables. But **none** of the three reviewer lanes predicted the **cosign v2/v3 attestation-storage-location split**:

- `cosign attest --type cyclonedx` with cosign v2.4.x writes to the legacy `.att` tag.
- `actions/attest-build-provenance@v4.1.0` writes SLSA to the OCI 1.1 referrer API.
- `cosign verify-attestation` in cosign v3.x reads OCI 1.1 referrers only (does not search the legacy `.att` tag).

The split surfaced **only during the first end-to-end runtime tag-burn** (`v0.1.0-rc-supply-chain-test`). Local verify showed 16/24 failures — and the failure messages were misleading ("found: SLSA, expected: cyclonedx") because cosign was finding the SLSA in OCI referrer and ignoring the CycloneDX in `.att`.

**Fix-forward** (commit `c74bcc5`): bump `cosign-release: 'v2.4.1' → 'v3.0.6'` in `release.yml` (forces cosign attest to write to OCI referrers), use explicit predicate URIs in justfile (skip the alias-resolution layer entirely). Re-tag (`v2`) → 24/24 green.

**Action for Epic 11:** ξ Approvals also touches cosign (HMAC signature on operator decisions, `just verify-approval` recipe). Plan a runtime end-to-end test BEFORE the static review pass, not after. The first tag-burn is the cheapest non-trivial integration test we have — use it as a checkpoint, not a closure ritual.

### L2: Documentation poisoning is a recurring, predictable pattern

Pass-2 of **both** Story 8.2 and Story 8.3 found the SAME class of bug:
- Pass-1 had fixed `release.yml` comments, `justfile` `CERT_ID`, and `docs/deployment-guide.md` to anchored regex.
- Pass-1 had MISSED the spec body's AC-2 text and the runtime-verification section that operators copy-paste from.
- The Completion Notes line "F1 lesson applied from the start" was literally false in both stories.

Pass-2 caught this in Story 8.2; the same reviewers caught the SAME pattern in Story 8.3. This is a reliable pattern, not a one-time miss.

**Action for Epic 11+:** in adversarial reviews, treat spec-body audit as a **separate sweep** from code audit. The verifier lane specifically should grep spec files for any quoted command/regex/code-snippet and verify exact-byte match against the live code/recipe.

### L3: Sigstore Rekor transparency-log entries are permanent

The deleted `v0.1.0-rc-supply-chain-test` tag's attestations live forever on Rekor. Deletion is registry-only. Per ADR-0008 §F7 the duplicate Rekor entries from re-tags are cosmetic, not security-relevant — but the **immutability** is a real operational consideration:

- Test-tag attestations contaminate the canonical workflow's Rekor history. Future audits will see entries for `v0.1.0-rc-supply-chain-test` (deleted tag) AND `v0.1.0-rc-supply-chain-test-v2` (current).
- Sigstore Fulcio cert subjects include the workflow-run-attempt URL (`/attempts/1`); failed-then-retried runs leave breadcrumbs.

**Action for Epic 11+:** explicitly document that test/rc tags will leave permanent Rekor entries in the operator-runbook. For shipping real releases, prefer a single `vX.Y.Z` over multiple `vX.Y.Z-rc1, -rc2, ...` iterations once the supply-chain pipeline is hardened.

### L4: Warm-cache release runs were ~4 min, not 30

Initial timeline estimate was 30-40 min per CI run (cold cache for arm64 QEMU base build + 7 services matrix). Actual: ~4 min both times. The buildx GHA cache from Story 8.4's earlier CI run was already warm — the v0.1.0-rc-supply-chain-test tag-burn benefited.

**Implication for Epic 8 closure speed:** the two-tag iteration (v1 → fix → v2) cost ~8 min total, not the 60-min I'd budgeted. The "burn-a-tag-as-integration-test" loop is fast enough to make the runtime-feedback approach (L1) explicitly preferable to "review-only-and-hope".

**Action for Epic 11+:** budget actual runtime-feedback cycles as ~5-10 min each, not 30. This shifts the cost-benefit of "validate via tag-burn vs validate via more static review" toward the former.

## Epic 8's 14-Row Finding Pattern (Worth Replicating)

Stories 8.2 (×2), 8.3, 8.4, and 8.6 each surfaced exactly **14 findings** in their first adversarial review pass. Story 8.2 pass-2 also surfaced 14. This is **not a coincidence** — it's a consistent feature of the 3-lane (Blind / Edge-Case-Security / Acceptance-Auditor) parallel-review pattern when each lane is prompted to find ≥8 findings:

- Blind Hunter: 8-9 findings (mostly correctness, style, edge cases)
- Edge-Case + Security: 8-10 findings (OWASP categories, race conditions, defense-in-depth)
- Acceptance Auditor: 6-10 findings (AC literal compliance, drift detection)
- After dedup across lanes: ~14 unique findings

**Action for Epic 11+:** keep the 3-lane pattern. Aim for similar finding density. **DO NOT** skip the pass-2 (second-opinion) review just because pass-1 returned 14 findings — pass-2 finds carry-overs and structural-fix-introduced-new-issues that the first pass cannot see (Story 8.2's 14+14 split is the proof point).

## Technical Debt Carried Forward (4 items)

1. **Node.js 20 deprecation warning** in release.yml — 6 actions still on Node 20 (checkout, upload-artifact, build-push-action, login-action, setup-buildx, setup-qemu). GitHub forces Node 24 by default June 2026. Plan: SHA-pin to Node-24 versions before deadline. **Severity: LOW** (advance warning only). Owner: future Epic 8.7 mini-sweep OR roll into Epic 11 hygiene cluster.
2. **Pre-existing test_migrations failures** (2) — revision mismatch (`Expected '0003', got: '0004'`). Pre-existing, repo-state drift from Phase 1 migration tooling. **Severity: LOW** (CI noise; PR-gate not blocked). Not Epic 8's responsibility but worth a separate fix sweep eventually.
3. **Test-isolation fragility** — `unregister_all()` autouse fixtures in `test_canonical.py` + `test_envelope.py` blast global REGISTRY between tests, requiring Story 8.6's local autouse re-register fixture as a workaround. Centralization in `tests/conftest.py` would fix this once for all current and future `events/types/*` modules. **Severity: LOW**. Owner: pre-Epic-11 hygiene (Epic 11 also adds new event types).
4. **`OMB_GHCR_OWNER` operator-rebindable trust anchor** (documented in ADR-0008 §"Known limitations" per Story 8.2 pass-2 F4). Threat model accepts this; legitimate forks need to verify against their own re-published images. Hardening would require a hardcoded canonical-owner allowlist with `--allow-custom-owner` opt-in. **Severity: ACCEPTED-AS-IS** for solo-operator threat model. Revisit if multi-operator deploys ever scope in.

## Process Improvements (3)

1. **Pass-2 reviews are not optional for Sigstore/cosign-touching stories.** Story 8.2 pass-2 caught 3 HIGH gaps; Story 8.3 pass-2 caught 2 HIGH gaps. Both passes resolved structural issues the first review couldn't see. Apply to Epic 11.
2. **Compressed `/bmad-create-story` + `/bmad-dev-story` single-session flow** is appropriate for small stories (8.3, 8.5, 8.6) but NOT for stories with substantial code surface (8.2 SLSA + 8.4 SBOM-attest were correctly authored as separate spec + dev passes). Heuristic: if the spec is <100 lines AND the diff is <50 lines, single-session is fine.
3. **"Fix all issues even minors" policy** (user instruction during Stories 8.2 / 8.4 reviews) was the right call — LOW-severity hygiene findings (code-comment WHY notes, `__all__` ordering, dead list comprehensions) compound into noticeable maintenance cost when ignored. Keep this as the default policy for Epic 11+.
