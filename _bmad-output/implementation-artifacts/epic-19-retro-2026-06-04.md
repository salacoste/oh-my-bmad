# Epic 19 Retrospective: χ artifact MCP server — content-addressed store, closes Phase 3 (Phase 3 Epic 6 of 6)

## Epic Summary

Epic 19 shipped `artifact-mcp` — a persisted build/run-output store over a **content-addressed**
local-FS backing store (sha256 → `objects/<hash[:2]>/<hash>`) with operator-configurable retention.
`get`/`list` (Tier-1), `put` (Tier-2), `delete` (Tier-3 approval-gated), emitting `artifact.stored`
+ `artifact.deleted`. Gated by ADR-0011. 5 stories, PRs #56–#59, all CI-green. **The final Phase-3
server — its merge closed Phase 3.** It combined the memory store-archetype with git/github's Tier-3
approval pattern.

## Story-by-Story Highlights

- **19.1 + 19.2 (PR #56):** ATDD + `ArtifactStore`. Content-addressed: `put` → sha256 → write-temp →
  fsync → `os.replace` (atomic; a crashed put leaves a sweepable orphan temp, never a corrupt
  object); `get` **re-hashes on read** (partial-write/tamper → mismatch → None) — content-addressing
  gives free dedup + integrity. Raw-sqlite3 index (reusing memory-mcp's pattern); 0o660/0o2775 file
  modes; retention `sweep()` (TTL + size-cap). No new dep (stdlib `hashlib` + `sqlite3`).
- **19.3 (PR #57):** `get`/`list`/`put`/`delete` tools; `delete` Tier-3 via `check_tier_with_approval`
  (denied without `approval.granted`). **Binary-safety fix caught by diff-audit:** the delegated pass
  made `put` take a UTF-8 string while `get` returned base64 — an asymmetric, text-only contract that
  *cannot store binary build output* (the artifact store's whole purpose). Changed `put` to accept
  base64; verified **all 256 byte values round-trip identically**.
- **19.4 (PR #58):** `artifact.stored` (put) + `artifact.deleted` (Tier-3 delete + retention sweep —
  system-initiated) events; metadata-only payloads (hash/name/size/reason — no bytes); the startup
  sweep is event-less (no caller trace_id at boot).
- **19.5 (PR #59):** S-9 separability (real subprocess + **binary** put→get round-trip through stdio
  + P3-I2) + allowlist (`ARTIFACT_MCP_*` + retention config, non-secret) + supply-chain. **Closed
  Epic 19 + Phase 3.**

## Key Lessons (3)

### L1: For a content store, the wire contract MUST be binary-safe — and symmetric
The 19.3 leak-of-correctness: a `put` that takes UTF-8 text and a `get` that returns base64 is
*asymmetric* and *can't store binary*. An artifact store exists to hold build/run output — compiled
binaries, tarballs, images — which is binary by nature. base64 for *both* directions is the only
correct contract. The S-9 test now proves arbitrary binary (256 byte values) survives a real
subprocess round-trip. Lesson: when a tool's purpose is "store arbitrary bytes," a text-only wire
format is a functional defect, not a nicety — diff-audit the *purpose*, not just the security.

### L2: Content-addressing buys integrity for free — use it
sha256-addressing means: dedup (same content → same path), tamper-detection (re-hash on read catches
partial writes / corruption), and atomic crash-safety (write-temp-then-rename leaves orphan temps,
never corrupt objects). The store got integrity guarantees from the addressing scheme itself, with no
extra checksums or journaling beyond WAL on the index.

### L3: System-initiated deletion is the one path that bypasses Tier-3 — bound it by policy
Retention-sweep deletions emit `artifact.deleted` but run *without* a Tier-3 approval, because they
are system-initiated and bounded by the operator-set policy (TTL / size-cap), not actor-initiated
(ADR-0011 §5). The Tier-3 gate is for *actor* deletions (`delete` tool). This distinction — policy-
bounded system action vs. authorized actor action — is the right model for any automated GC.

## Technical Debt Carried Forward
- None new. A retention sweep at very large object counts is an O(n) index scan; fine at current
  scale, revisit if the store grows large.

## Action Items (1)
- **AI-19.1 (DONE in-epic):** the base64-symmetric-wire + content-addressing + metadata-only-event
  pattern is documented for any future blob/content store.

## Process Improvements (1)
- **Diff-audit the PURPOSE, not only the security + style.** The binary-safety gap was gate-green,
  security-clean, and style-correct — but defeated the server's reason to exist. The diff-audit lens
  must include "does this contract actually serve the stated purpose?" (here: store arbitrary bytes).

## Acceptance gate

  permitted with it.
- ✅ Retention enforced (sweep at startup + on `put`); store isolated in its own subtree (P3-I2),
  never the registry DB.
- ✅ `artifact.*` events (incl. retention `artifact.deleted`) with `trace_id`; registered + green.
