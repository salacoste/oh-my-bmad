## Key Lessons (3 — net-new vs Epic 8)

### L1: Green gates mask the next failure — the "hidden cascade" pattern

When CI has been red for weeks, ONE fix never closes the loop. Each green gate exposes a fresh failure that was waiting behind it. The first commit (`6f1fc3c`) cleared ruff but immediately exposed mypy. The mypy fix exposed missing test deps. Those exposed a workspace-manifest bug. That exposed a Python module-cache test-isolation cascade. That exposed an aiosqlite teardown race.

This is **not coincidence** — it's the natural shape of accumulated CI debt. Every gate in the pipeline depends on the prior one running to completion; when the early gates fail, the later ones never get a chance to run, so their breakages sit latent.

**Implication for future debt sweeps:**
- Budget for at least 2× the planned commit count.
- Don't celebrate after the first green local run — push, wait, and watch the next gate fall.
- Burn CI cycles aggressively. The marginal cost of one more `git push` is much cheaper than guessing at the next blocker.
- Phase the work mentally: original scope ("the 4 stories") vs cascade-discovery scope ("everything that surfaces in CI").

### L2: Python module cache + `unregister_all()` = registration-time bombs

`event_types.py` registers ~50 event types via module-level `register()` calls. Python imports a module **once per process**; module-level statements don't re-run. Sibling test files calling `unregister_all()` to test the registry's teardown semantics leave the registry empty for the rest of the test session — but only the **next** test that depends on a registration discovers this.

The fix pattern is now established (Story 8.6's `_ensure_deployment_registered` was the trailblazer):

1. Extract module-level `register()` calls into an `ensure_registered()` function.
2. Call `ensure_registered()` at module bottom (preserves the import-time side effect for production code).
3. Re-call `ensure_registered()` in an autouse fixture inside any test file that runs after `unregister_all()` siblings.

**Implication for Epic 11+:** every new event type added to `event_types.py` should be inside `ensure_registered()`. Reviewers should treat bare `register()` at module scope as a smell.

### L3: GHA `bash -e` aborts your error-handling code before it runs

GitHub Actions `run:` blocks execute under `bash -e` by default. If the command you're trying to error-handle returns non-zero, `set -e` kills the script **before** your `if`/`else`/exit-code-translator code can fire. Three rounds of commits (`011ced6` → `c3d8222` → `a0c53bb`) were spent fighting this:

1. `011ced6` — wrote the tolerance shim. Logic bug in the `! grep | grep -v` chain.
2. `c3d8222` — fixed the grep logic. Shim still never ran.
3. `a0c53bb` — added `set +e`. Shim ran. CI green.

**Implication for any GHA step that wraps a non-zero-prone command:** always start with `set +e` (or `shell: bash` without `-e`). Capture exit codes via `$?` immediately, then re-enable strict mode after the decision logic.

## Technical Debt Carried Forward

1. **Story 8.7.5 (test-isolation centralization)** — the per-file `ensure_registered()` autouse pattern works but doesn't scale. Future event types added to `event_types.py` require every downstream test file to know to call `ensure_registered()` in its fixture. A `tests/conftest.py`-level session-scoped autouse fixture would centralize this. (Originally listed as Epic 8 retro debt item #3; partially resolved by `ensure_registered()`, fully resolvable by centralizing.)

2. **Story 8.7.6 (aiosqlite daemon-thread teardown)** — current CI relies on a bash exit-code-tolerance shim. The real fix is one of:
   - Switch `asyncio_default_fixture_loop_scope` from per-test to `module` / `session` so worker threads don't accumulate across 2376 tests.
   - Migrate the affected suites to a synchronous SQLite driver.
   - Add a session-scoped autouse fixture that explicitly disposes lingering async engines.

   Risk of the current shim: a genuine SIGABRT that happens to land after a green summary line will be silently tolerated. The grep matcher requires "passed" AND no "failed" in the summary, but an indeterminate result (timeout, kill -9) could in principle slip through.

3. **2189 vs 2376 test count divergence** — local runs see 2189; CI sees 2376. Suggests test-discovery differences (likely `tests/` directory excluded by local pytest config). Worth confirming the local pytest invocation matches CI to avoid local-green-but-CI-red surprises.

4. **Two-config mypy** — `mypy.ini` is canonical but `pyproject.toml` had a stray `[tool.mypy]` section earlier in the sweep that took precedence. Future readers may not realise mypy reads `mypy.ini` over `[tool.mypy]` when both exist. Worth a one-line comment in `mypy.ini` and a Sphinx-style cross-reference in `pyproject.toml`.

## Process Improvements

1. **The "hidden gate" question is now a planning checklist item.** Before declaring any debt-sweep story scoped/complete, explicitly ask: "what gate ran AFTER the one we fixed, and is it still red on CI?" Epic 8.7 originally scoped 4 stories; an explicit "what could be hidden behind these" pass would have surfaced the secret-hygiene + capabilities-workspace + module-cache issues earlier.

2. **Don't trust local pytest alone.** Local runs saw 2189 tests; CI saw 2376. Any "all green locally" claim should be paired with a CI push before any sprint-status update. (This bit us at `commit 46ecb88` — we marked 8.7 closed before CI had even seen the changes.)

3. **Read CI logs before writing follow-up commits.** Several iterations could have been skipped if the failing log was read end-to-end first instead of fixing the most prominent error and re-pushing. Specifically the `bash -e` issue was visible in the GHA `Run` block echo — the script's `if/exit` lines were never printed, which would have been the clue to look for `set +e`.
