## Story

As **R2d2 (operator + sole maintainer)**,
I want **every Platform-published Docker image to carry a SLSA Build Level 2 provenance attestation**,
so that **the operator's deploy-side `cosign verify-attestation --type slsaprovenance` can prove an image was built by the canonical `release.yml` workflow on a specific commit SHA — closing the second of three supply-chain triumvirate gates (cosign signature in Story 8.3, SBOM attestation in Story 8.4)**.

## Acceptance Criteria

1. **(AC-1)** Every image published by `release.yml` (1 base + 7 services = 8 images per release) carries a SLSA L2 provenance attestation pushed to the OCI registry alongside the image, generated by `actions/attest-build-provenance` against the image's content digest.
2. **(AC-2)** `cosign verify-attestation --type slsaprovenance --certificate-identity-regexp "https://github.com/${OWNER}/oh-my-bmad/.github/workflows/release.yml.*" --certificate-oidc-issuer "https://token.actions.githubusercontent.com" <image>@<digest>` succeeds for every released image; the attestation traces back to the specific commit SHA + workflow run ID that built it.

## Dev Notes

### Why SLSA L2, not L1 or L3+

- **SLSA L1** (build provenance exists) is too weak — `docker buildx` already produces unsigned provenance metadata; doesn't prove who built the image.
- **SLSA L2** (signed provenance from a hosted build platform) is what `actions/attest-build-provenance` produces: provenance signed by GitHub's keyless Sigstore identity, traceable to a specific workflow run + commit SHA. **Right tier for the project's threat model** (solo operator, public GHCR, hostile-mirror substitution as the primary attack).
- **SLSA L3+** would require hermetic, parameterless, isolated builds — beyond `actions/attest-build-provenance`'s scope and out-of-budget for Phase 2. Deferred to Phase 4+ if operational scope expands (per ADR-0008).

### Why `actions/attest-build-provenance`, not `slsa-framework/slsa-github-generator`

- `actions/attest-build-provenance` is **GitHub-first-party**, maintained by the GitHub Actions team. Same OIDC chain as cosign keyless (Story 8.3) → one trust root, two attestation types.
- `slsa-framework/slsa-github-generator` is community-maintained, more configurable (supports SLSA L3 patterns with worker-orchestration), but adds a second supply-chain trust root (the slsa-framework team's signing infrastructure). Increases trust-perimeter for marginal gain at L2.
- **Decision locked in ADR-0008** §"GitHub-first-party SLSA over external Sigstore CI". Re-read the ADR if reconsidering.

### Action input details (from `actions/attest-build-provenance@v4.1.0` documentation)

Required inputs:
- `subject-name`: the registry-prefixed image reference *without* the digest suffix (e.g., `ghcr.io/<owner>/oh-my-bmad-base`). The action appends the digest automatically.
- `subject-digest`: the image's SHA256 content digest (e.g., `sha256:abc...`), as output by `docker/build-push-action`'s `digest` output.
- `push-to-registry: true`: tells the action to publish the attestation to the OCI registry alongside the image, instead of only making it queryable via the GitHub Attestations API.

The action handles OIDC token minting, Sigstore Fulcio cert request, signing, and registry upload internally. No additional config needed.

### Where the digest comes from in our workflow

Existing release.yml (lines 84–101 for base, lines 143–161 for services) already passes `id: build` to `docker/build-push-action`. The build action's output `digest` is documented stable: `${{ steps.build.outputs.digest }}` returns `sha256:abc123...` after a successful multi-arch push. **No extra configuration needed in the build step.**

### Where to insert the steps

For consistency with Story 8.1's pattern, insert the SLSA attestation step **after the `:latest` tagging step**, sharing the section's commentary block. Suggested location:

- **Base job:** after `Tag base as :latest`, before the SBOM generation steps (so the SLSA attestation is a sibling supply-chain artifact to the SBOM rather than ordered through it).
- **Matrix job:** after `Tag <service> as :latest`, before the SBOM steps.

This ordering is operationally arbitrary (both attestations and SBOMs run on the same content digest), but visually groups supply-chain operations together.
