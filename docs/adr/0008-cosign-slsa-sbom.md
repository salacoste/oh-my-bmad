# ADR-0008: cosign keyless + SLSA L2 + CycloneDX SBOM as the supply-chain triumvirate

## Status

**Accepted** — 2026-05-15. Promoted from `proposed` upon Epic 8 Story 8.1 merge (commit `c5a914c` + SHA-pin follow-up). Story 8.1 ships the SBOM-generation half of the triumvirate; Stories 8.2 (SLSA L2), 8.3 (cosign keyless sign), and 8.4 (attach SBOM as attestation) complete the loop; Story 8.5 ships the deploy-side `just verify-images` gate.

## Context

Phase 1 published Docker images to GHCR with tag-based versioning only ([`docs/architecture.md`](../../docs/architecture.md) §"Phase-2 hooks", "Status: scaffold (Story 1.1)"). The image-pull integrity line in Phase 1 was a single GHCR setting (tag-immutability) plus operator trust that the registry hadn't been compromised. No cryptographic verification of provenance, no machine-readable bill of materials, no third-party-verifiable signature.

Phase 2 Epic 8 (γ Supply-chain hardening) closes this gap. The PRD amendment ([`prd.md`](../../_bmad-output/planning-artifacts/prd.md) FR53–FR56a, NFR-S9, NFR-S11) and the architecture amendment ([`architecture.md`](../../_bmad-output/planning-artifacts/architecture.md) §"Supply-chain pipeline (γ — Epic 8)") collectively specify three independent verification mechanisms that must all hold on every released image. This ADR names them, picks specific implementations, and forecloses alternatives.

The three mechanisms answer three different questions:

| Mechanism | Question it answers | Failure mode it prevents |
|---|---|---|
| **cosign keyless signature** | "Who built this image, in what GitHub Actions workflow run?" | A compromised registry can't substitute a malicious image — the operator's deploy-side `cosign verify` fails. |
| **SLSA L2 build provenance** | "What source commit + workflow produced this image? Was the build process tamper-evident?" | Attacker can't claim a malicious build was produced by the canonical workflow — the provenance attestation binds image digest to workflow run + commit SHA. |
| **CycloneDX SBOM** | "What's actually inside this image — direct deps, transitive deps, license identifiers?" | Operator can audit dependencies post-hoc (CVE response, license-incompatibility detection) without rebuilding the image. License-scan at publish time blocks GPL-tainted releases. |

Each mechanism is independently useful. Bundling all three is what we're committing to.

## Decision

1. **Every Platform-published Docker image carries all three artifacts** as OCI attestations attached to the image's content digest:
   - cosign keyless signature against the GitHub Actions OIDC identity for `github.com/${OWNER}/oh-my-bmad`.
   - SLSA Build Level 2 provenance attestation generated by `actions/attest-build-provenance` (GitHub's first-party SLSA generator — no separate Sigstore infrastructure required).
   - CycloneDX (not SPDX) SBOM generated by `anchore/sbom-action` and attached as a cosign attestation of type `cyclonedx`.

2. **Phase 1 release pipeline** (`.github/workflows/release.yml`) is the only path that produces these artifacts. Manual `docker push` outside the workflow is forbidden (existing operator-discipline rule from Phase 1; reaffirmed here).

3. **Operator deploy paths verify all three** before pulling a release image:
   - `cosign verify` checks the signature's certificate identity matches the canonical GitHub Actions OIDC issuer.
   - `cosign verify-attestation --type slsaprovenance` checks the SLSA L2 attestation traces back to a workflow run + commit SHA on this repository.
   - `cosign verify-attestation --type cyclonedx` retrieves the SBOM; a deploy-side license check refuses images whose SBOM lists non-allowlisted SPDX identifiers.

4. **Verification is enforced via `just verify-images`** (Story 8.5) before `docker compose pull`. Verification failure refuses the pull and emits a `deployment.signature_rejected` event (Story 8.6).

5. **Third-party action pinning policy preserved.** Every new sigstore + anchore + GitHub-first-party action used in `release.yml` is SHA-pinned with a `# vX.Y` comment, matching the existing Phase 1 convention (`actions/checkout@<sha>  # v4`). Upgrade procedure: bump SHA + comment together; review the action's release notes for breaking changes before merging.

6. **CycloneDX over SPDX.** Both are valid OCI-attestation SBOM formats. CycloneDX is chosen because:
   - `anchore/sbom-action`'s native output format is CycloneDX (no transcoding step).
   - CycloneDX JSON is more easily diffed in PR reviews than SPDX tag-value format.
   - Operator tooling (license-scan recipes) reads CycloneDX directly without conversion.

7. **GitHub-first-party SLSA over external Sigstore CI.** `actions/attest-build-provenance` produces SLSA L2 attestations using the same OIDC identity as cosign keyless — one OIDC chain, two attestation types. External Sigstore CI infrastructure (Rekor instance, Fulcio CA) would add a second trust root for marginal additional security. **Defer Sigstore-private-CA + Notary v2 to Phase 4+** if the threat model expands beyond solo-operator use.

## Consequences

**Operational:**

- Release-pipeline runtime increases by ~3–5 minutes (SBOM generation + cosign sign + cosign attest per service × 8 services). Phase 1's release was ~12 minutes; Phase 2 baseline is ~15–17 minutes. Acceptable trade-off.
- The `permissions:` block on `release.yml` gains `id-token: write` (required for cosign keyless OIDC) and `attestations: write` (required for SLSA provenance). These permissions scope to the workflow only; `GITHUB_TOKEN` privileges elsewhere are unchanged.
- Operator's `.env` gains `OMB_IMAGE_DIGEST_<service>` entries (one per service) for digest-pinned references. Tag-based references (`OMB_VERSION`) remain supported as a Phase 1 cutover fallback and are deprecated in Phase 3.

**Security:**

- Phase 1's tag-immutability setting is preserved as the second line of defense (defense in depth). A compromised release pipeline that could sign a malicious image would still face the immutable-tag setting at the registry layer.
- Operator-local `cosign` binary is a new dependency on the deploy host. Documented in `docs/deployment-guide.md` and `docs/deployment/{vps,macos}.md` updates landing alongside Story 8.5.

**Workflow:**

- Phase 2 implementation cycle for Epic 8 (Stories 8.1–8.6) takes ~3 days of solo-operator work. Story 8.1 ships SBOM generation first (no signing yet — proves the pipeline produces valid SBOMs). Stories 8.2 (SLSA) + 8.3 (cosign sign) + 8.4 (SBOM attached as attestation) land sequentially. Story 8.5 (`just verify-images`) closes the deploy-side loop. Story 8.6 (the `deployment.signature_rejected` event) closes the audit-trail loop.
- Any Phase 2 epic's release (Epic 9–13) ships through the new pipeline once Epic 8 is `done`. **Epic 8 is a hard prerequisite for any other Phase 2 epic merging to `main`.**

**Future:**

- Phase 3 hardening (when scoped): Sigstore private-CA + Rekor private instance for organizational use; Notary v2 for runtime image-pull policy enforcement; image-signing key rotation procedure.
- Phase 4+: SBOM-based vulnerability scanning in nightly CI (against an offline CVE database) producing automated update PRs.

## Alternatives considered

- **Sigstore-private-CA + Notary v2 in Phase 2.** Rejected — solo-operator threat model does not justify a second trust root + the operational overhead of a private Rekor instance. Defer to Phase 4+ if multi-operator scope materializes.
- **SPDX instead of CycloneDX.** Rejected — see Decision §6.
- **`syft` binary directly via curl-pipe-to-bash.** Rejected — ironic to bootstrap supply-chain hardening with an unverified install script. `anchore/sbom-action` (which wraps syft) is SHA-pinned the same way every other third-party action is.
- **Defer all three mechanisms to a single Story 8.7 mega-implementation.** Rejected — breaking Epic 8 into 6 atomic stories (one per mechanism + one for the deploy-side gate + one for the audit event) makes per-story review tractable and per-story rollback safe.
- **Phase 1 tag-immutability is enough.** Rejected — tag-immutability protects against post-publish tampering only. It does not prove who published the image, what they built, or what's inside. The three Phase 2 mechanisms answer the three load-bearing questions tag-immutability cannot.
