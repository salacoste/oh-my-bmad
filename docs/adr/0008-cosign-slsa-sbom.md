# ADR-0008: cosign keyless + SLSA L2 + CycloneDX SBOM as the supply-chain triumvirate

## Status

**Accepted** — 2026-05-15. Promoted from `proposed` upon Epic 8 Story 8.1 merge (commit `c5a914c` + SHA-pin follow-up). Story 8.1 ships the SBOM-generation half of the triumvirate; Stories 8.2 (SLSA L2), 8.3 (cosign keyless sign), and 8.4 (attach SBOM as attestation) complete the loop; Story 8.5 ships the deploy-side `just verify-images` gate.

## Context

Phase 1 published Docker images to GHCR with tag-based versioning only ([`docs/architecture.md`](../../docs/architecture.md) §"Phase-2 hooks", "Status: scaffold (Story 1.1)"). The image-pull integrity line in Phase 1 was a single GHCR setting (tag-immutability) plus operator trust that the registry hadn't been compromised. No cryptographic verification of provenance, no machine-readable bill of materials, no third-party-verifiable signature.

Phase 2 Epic 8 (γ Supply-chain hardening) closes this gap. The PRD amendment ([`prd.md`](../../_bmad-output/planning-artifacts/prd.md) FR53–FR56a, NFR-S9, NFR-S11) and the architecture amendment ([`architecture.md`](../../_bmad-output/planning-artifacts/architecture.md) §"Supply-chain pipeline (γ — Epic 8)") collectively specify three independent verification mechanisms that must all hold on every released image. This ADR names them, picks specific implementations, and forecloses alternatives.

The three mechanisms answer three different questions:

| Mechanism | Question it answers | Failure mode it prevents |
|---|---|---|
| **cosign keyless signature** | "Who built this image, in what GitHub Actions workflow run?" | A compromised registry can't substitute a malicious image — the operator's deploy-side `cosign verify` fails. |
| **SLSA L2 build provenance** | "What source commit + workflow produced this image? Was the build process tamper-evident?" | Attacker can't claim a malicious build was produced by the canonical workflow — the provenance attestation binds image digest to workflow run + commit SHA. |
| **CycloneDX SBOM** | "What's actually inside this image — direct deps, transitive deps, license identifiers?" | Operator can audit dependencies post-hoc (CVE response, license-incompatibility detection) without rebuilding the image. License-scan at publish time blocks GPL-tainted releases. |

Each mechanism is independently useful. Bundling all three is what we're committing to.

## Decision

1. **Every Platform-published Docker image carries all three artifacts** as OCI attestations attached to the image's content digest:
   - cosign keyless signature against the GitHub Actions OIDC identity for `github.com/${OWNER}/oh-my-bmad`.
   - SLSA Build Level 2 provenance attestation generated by `actions/attest-build-provenance` (GitHub's first-party SLSA generator — no separate Sigstore infrastructure required).
   - CycloneDX (not SPDX) SBOM generated by `anchore/sbom-action` and attached as a cosign attestation of type `cyclonedx`.

2. **Phase 1 release pipeline** (`.github/workflows/release.yml`) is the only path that produces these artifacts. Manual `docker push` outside the workflow is forbidden (existing operator-discipline rule from Phase 1; reaffirmed here).

3. **Operator deploy paths verify all three** before pulling a release image:
   - `cosign verify` checks the signature's certificate identity matches the canonical GitHub Actions OIDC issuer.
   - `cosign verify-attestation --type slsaprovenance` checks the SLSA L2 attestation traces back to a workflow run + commit SHA on this repository.
   - `cosign verify-attestation --type cyclonedx` retrieves the SBOM; a deploy-side license check refuses images whose SBOM lists non-allowlisted SPDX identifiers.

4. **Verification is enforced via `just verify-images`** (Story 8.5) before `docker compose pull`. Verification failure refuses the pull and emits a `deployment.signature_rejected` event (Story 8.6).

5. **Third-party action pinning policy preserved.** Every new sigstore + anchore + GitHub-first-party action used in `release.yml` is SHA-pinned with a `# vX.Y` comment, matching the existing Phase 1 convention (`actions/checkout@<sha>  # v4`). Upgrade procedure: bump SHA + comment together; review the action's release notes for breaking changes before merging.

6. **CycloneDX over SPDX.** Both are valid OCI-attestation SBOM formats. CycloneDX is chosen because:
   - `anchore/sbom-action`'s native output format is CycloneDX (no transcoding step).
   - CycloneDX JSON is more easily diffed in PR reviews than SPDX tag-value format.
   - Operator tooling (license-scan recipes) reads CycloneDX directly without conversion.

7. **GitHub-first-party SLSA over external Sigstore CI.** `actions/attest-build-provenance` produces SLSA L2 attestations using the same OIDC identity as cosign keyless — one OIDC chain, two attestation types. External Sigstore CI infrastructure (Rekor instance, Fulcio CA) would add a second trust root for marginal additional security. **Defer Sigstore-private-CA + Notary v2 to Phase 4+** if the threat model expands beyond solo-operator use.

## Consequences

**Operational:**

- Release-pipeline runtime increases by ~3–5 minutes (SBOM generation + cosign sign + cosign attest per service × 8 services). Phase 1's release was ~12 minutes; Phase 2 baseline is ~15–17 minutes. Acceptable trade-off.
- The `permissions:` block on `release.yml` gains `id-token: write` (required for cosign keyless OIDC) and `attestations: write` (required for SLSA provenance). These permissions scope to the workflow only; `GITHUB_TOKEN` privileges elsewhere are unchanged.
- Operator's `.env` gains `OMB_IMAGE_DIGEST_<service>` entries (one per service) for digest-pinned references. Tag-based references (`OMB_VERSION`) remain supported as a Phase 1 cutover fallback and are deprecated in Phase 3.

**Security:**

- Phase 1's tag-immutability setting is preserved as the second line of defense (defense in depth). A compromised release pipeline that could sign a malicious image would still face the immutable-tag setting at the registry layer.
- Operator-local `cosign` binary is a new dependency on the deploy host. Documented in `docs/deployment-guide.md` and `docs/deployment/{vps,macos}.md` updates landing alongside Story 8.5.

**Workflow:**

- Phase 2 implementation cycle for Epic 8 (Stories 8.1–8.6) takes ~3 days of solo-operator work. Story 8.1 ships SBOM generation first (no signing yet — proves the pipeline produces valid SBOMs). Stories 8.2 (SLSA) + 8.3 (cosign sign) + 8.4 (SBOM attached as attestation) land sequentially. Story 8.5 (`just verify-images`) closes the deploy-side loop. Story 8.6 (the `deployment.signature_rejected` event) closes the audit-trail loop.
- Any Phase 2 epic's release (Epic 9–13) ships through the new pipeline once Epic 8 is `done`. **Epic 8 is a hard prerequisite for any other Phase 2 epic merging to `main`.**

**Known limitations (documented for transparency; not blocking deployment):**

- **Multi-arch SBOM represents amd64 only.** All Platform images are multi-arch (`linux/amd64,linux/arm64`). `anchore/sbom-action` pulls the image from GHCR using the GitHub Actions runner's native architecture (`ubuntu-24.04` = amd64) and scans only that platform. The resulting CycloneDX SBOM is attached as an attestation against the manifest-index digest (which covers both arches). An arm64 operator pulling the attestation therefore receives an **amd64-derived** SBOM. The dependency graph is identical across arches in practice (Python wheels are largely arch-agnostic) but the runtime-resolved layer hashes differ. Per-arch SBOM generation is deferred to Phase 3+ (requires a matrix-over-arch SBOM step + multiple attestations per image — non-trivial workflow change).
- **SLSA L2 attestation IS multi-arch** (Story 8.2 code-review pass-2 F13 clarification). `actions/attest-build-provenance` binds the attestation to the manifest-index content digest (which references both amd64 and arm64 platform manifests). `cosign verify-attestation --type slsaprovenance` resolves the manifest-index correctly regardless of the verifier's native architecture, so an arm64 operator and an amd64 operator see identical SLSA provenance for the same image. This asymmetry between SLSA (multi-arch correct) and SBOM (amd64-only) is intentional given the cost asymmetry: SLSA captures *build-source provenance* which is platform-invariant; SBOM captures *runtime layer composition* which is platform-specific.
- **`cosign attest --type cyclonedx` alias resolution.** The `cyclonedx` alias resolves to the in-toto predicate type URI `https://cyclonedx.org/bom`. cosign verify-attestation accepts the alias consistently, so round-trip verification works end-to-end. However, **Dependency-Track v4.11+** introduced strict spec-version matching (`https://cyclonedx.org/bom/v1.4` vs `v1.5` vs `v1.6`). Operators pointing DT at the GHCR attestations may need to configure DT to accept the version-agnostic URI explicitly. Other CycloneDX consumers (OSV-Scanner, Trivy, syft) accept the version-agnostic URI without configuration. Documented limitation; not a defect.
- **Push-→-attest TOCTOU mitigated by digest-binding** (Story 8.2 code-review pass-2 F10). Between `docker/build-push-action` (push) and `actions/attest-build-provenance` (sign attestation) the image exists in GHCR as a content-addressed manifest. The attestation binds to the **content digest** (`steps.build.outputs.digest`), NOT the mutable tag. Even if a concurrent malicious push were to repoint the tag between these two workflow steps, the attestation remains cryptographically bound to the original digest — `just verify-images` uses digest-based references (`<image>@sha256:...`) and will detect any digest mismatch immediately. GHCR tag-immutability is defense-in-depth, not the primary defence.
- **Operator-rebindable `OMB_GHCR_OWNER` is a documented trust-boundary** (Story 8.2 code-review pass-2 F4). The `just verify-images` recipe interpolates `OMB_GHCR_OWNER` from `.env` into the `cert-identity-regexp`. This means the trust root for cosign verification is operator-controlled, not hard-coded. The recipe emits a warning (suppressible via `OMB_ACK_CUSTOM_OWNER=1`) when the value differs from the canonical upstream owner. The threat model accepts this: legitimate forks need to verify against their own re-published images; an attacker who can write the operator's `.env` already has filesystem access and can bypass any verification. The warning is operator-friendly hardening, not a security boundary.

**Future:**

- Phase 3 hardening (when scoped): Sigstore private-CA + Rekor private instance for organizational use; Notary v2 for runtime image-pull policy enforcement; image-signing key rotation procedure.
- Phase 4+: SBOM-based vulnerability scanning in nightly CI (against an offline CVE database) producing automated update PRs.

## Operational policy notes (added per Story 8.2 code review)

### Tag-retry duplicate attestations (F7)

If a release-tag push is retried (operator re-pushes the same `v*` tag, GH Actions runner failure mid-job, or `gh run rerun` after partial failure), **all three Sigstore-bound steps** run again against the same image digest:

1. `actions/attest-build-provenance` (SLSA L2 — Story 8.2) → new Rekor entry for the SLSA predicate.
2. `cosign sign` (Story 8.3) → new Rekor entry for the signature.
3. `cosign attest --type cyclonedx` (Story 8.4) → new Rekor entry for the SBOM predicate.

Because Sigstore Fulcio mints a new cert per invocation and Rekor's transparency log is append-only, this produces **three new attestation entries** per retry for the same `(subject-name, subject-digest)` triple.

This is **cosmetic, not a security issue.** All entries are valid; `cosign verify` / `cosign verify-attestation` return the first matching one. The duplicates are auditor-visible in Rekor but do not produce verification failures.

**Mitigation:** Use `gh run rerun` only when the build step itself failed (in which case none of the three attestations ran on the first attempt). If any Sigstore-bound step succeeded and a downstream step failed, prefer fixing the downstream step in a follow-up commit + new tag rather than re-running the entire release.

### Sigstore Fulcio / Rekor outage = hard release block (F8)

`actions/attest-build-provenance` does not include retry or graceful-degradation logic. If Sigstore's Fulcio (cert minting) or Rekor (transparency log) is unreachable, the step fails and the entire matrix entry (or base job) fails. **This is intentional, not a gap.**

The trade-off:
- **Pros of hard-block:** every released image is provably attested; operator never deploys an unattested image. Matches the security-first stance of the supply-chain triumvirate.
- **Cons of hard-block:** Sigstore outage = release pipeline outage. Operator cannot ship a fix-forward until Sigstore recovers.
- **Cons of soft-fail (rejected):** silently shipping unattested images defeats the entire AC-2 gate. Operators have no signal that the image they're pulling lacks an attestation.

**Operational consequence:** during a Sigstore outage, releases pause. Monitor https://status.sigstore.dev (or the Sigstore Slack #status channel) when troubleshooting a stuck release. No code change required to "fix" — the outage will resolve.

### Failure asymmetry across the supply-chain triumvirate (F12)

The release pipeline runs **three independent Sigstore-bound steps** per image per release: SLSA L2 attestation (Story 8.2), cosign keyless sign (Story 8.3), cosign attest SBOM (Story 8.4). Each can succeed or fail independently. The SBOM-gen step (Story 8.1 — local file, not Sigstore-bound) is the upstream precondition for Story 8.4 only.

This produces **eight terminal states** per service per release (using `S` = success, `F` = failure):

| State | SLSA | Sign | SBOM-attest | Operator action |
|---|---|---|---|---|
| **All-green** | ✓ | ✓ | ✓ | Deploy normally. `just verify-images` (Story 8.5) passes all three gates. |
| **SLSA-only** | ✓ | ✗ | ✗ | **Do not deploy.** No signature → cannot verify image provenance via `cosign verify`. Re-tag or fix-forward. |
| **Sign-only** | ✗ | ✓ | ✗ | **Do not deploy.** Signature lacks SLSA backing; missing SBOM attestation. Investigate Sigstore outage; re-tag. |
| **Attest-only** | ✗ | ✗ | ✓ | **Do not deploy.** SBOM is present in registry but image is unsigned and unattested for provenance. Re-tag. |
| **SLSA + sign, no SBOM-attest** | ✓ | ✓ | ✗ | **Do not deploy.** Image is provably built + signed but lacks the registry-resident SBOM attestation. Story 8.1's 90-day workflow-artifact SBOM may still exist, but `just verify-images` checks for the OCI attestation specifically and will refuse. Re-run cosign attest step (Story 8.4) independently, or re-tag. |
| **SLSA + SBOM-attest, no sign** | ✓ | ✗ | ✓ | **Do not deploy.** Image has provenance + bill of materials but no signature. Re-run cosign sign (Story 8.3) independently, or re-tag. |
| **Sign + SBOM-attest, no SLSA** | ✗ | ✓ | ✓ | **Do not deploy.** Image is signed + has SBOM but lacks the SLSA L2 provenance attestation. Re-tag (SLSA failures typically indicate Sigstore Fulcio outage). |
| **All-fail** | ✗ | ✗ | ✗ | **Do not deploy.** Build succeeded but no supply-chain artifacts. Investigate Sigstore outage; wait for recovery, then re-tag. |

The supply-chain triumvirate is **all-or-nothing for deployment safety**. `just verify-images` (Story 8.5) is the deploy-side gate that enforces this — refuses `docker compose pull` if any of the three attestations is missing.

**Note on partial-rerun:** cosign sign (Story 8.3) and cosign attest SBOM (Story 8.4) are independently re-runnable against an existing image digest from a local cosign installation — operator does not need to re-tag the release for these two. SLSA attestation re-run requires re-running the GitHub Actions workflow (only the action has the OIDC token issuance pathway). Document the operator-side rerun procedure in `docs/deployment-guide.md` when Story 8.5 lands.

## Alternatives considered

- **Sigstore-private-CA + Notary v2 in Phase 2.** Rejected — solo-operator threat model does not justify a second trust root + the operational overhead of a private Rekor instance. Defer to Phase 4+ if multi-operator scope materializes.
- **SPDX instead of CycloneDX.** Rejected — see Decision §6.
- **`syft` binary directly via curl-pipe-to-bash.** Rejected — ironic to bootstrap supply-chain hardening with an unverified install script. `anchore/sbom-action` (which wraps syft) is SHA-pinned the same way every other third-party action is.
- **Defer all three mechanisms to a single Story 8.7 mega-implementation.** Rejected — breaking Epic 8 into 6 atomic stories (one per mechanism + one for the deploy-side gate + one for the audit event) makes per-story review tractable and per-story rollback safe.
- **Phase 1 tag-immutability is enough.** Rejected — tag-immutability protects against post-publish tampering only. It does not prove who published the image, what they built, or what's inside. The three Phase 2 mechanisms answer the three load-bearing questions tag-immutability cannot.
